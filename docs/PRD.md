이 문서는 제품이 해결할 문제, 사용자 경험, 기능 범위와 완료 기준을 정의한다. 대상 사용자는 사용자가 정한 정의를 반영했으며, 별도로 합의하지 않은 제품 목표와 범위는 검토를 위한 제안이다. **현재 구현은 코드에서 확인한 기능을 의미하며, 실제 모델·외부 서비스·운영 환경에서 검증을 완료했다는 의미는 아니다.** 이 문서 작성 시 테스트·빌드·실서비스 호출은 실행하지 않았다.

## 1. 제품 개요

### 1.1 해결할 문제

여행을 준비하는 사용자는 관광지·날씨·숙소·식당 정보를 여러 서비스에서 찾고, 자신의 여행 조건에 맞춰 다시 정리해야 한다. 조건을 바꾸면 검색과 일정 정리를 반복해야 하며, 추천 정보의 출처와 최신 여부도 확인하기 어렵다.

### 1.2 제품 목표

사용자가 대화로 여행 조건을 정리하고, 필요한 정보를 조회해 수정 가능한 여행 계획을 얻도록 한다.

- 필수 조건을 한 번에 모두 입력하지 않아도 대화를 이어가며 수집한다.
- 수집한 조건을 먼저 보여 주고, 사용자가 동의하면 계획을 작성한다.
- 장소·날씨·숙소 등의 조회 결과와 추정·미확인 정보를 구분한다.
- 조회 실패나 예보 부재가 있어도 확인 가능한 정보와 남은 확인 사항을 전달한다.
- 같은 대화에서 조건을 바꾸고 계획을 다시 작성할 수 있게 한다.

### 1.3 대상 사용자와 핵심 시나리오

대상 사용자는 **여행을 스스로 계획하고 다녀올 수 있는 역량과 경제력을 갖춘 20~40대의 국내 성인**이다.

이는 제품의 대상 사용자 정의이며, 실제 사용자 조사와 수요 검증은 아직 수행하지 않았다. **MVP의 여행 지원 범위는 국내 여행으로 한정한다.**

| 사용자 상황 | 필요한 도움 | 기대 결과 |
|---|---|---|
| 목적지와 기간만 정함 | 필요한 조건 확인과 장소 탐색 | 자신의 조건에 맞는 여행 계획 |
| 여행 날짜와 취향이 정해짐 | 관광지·날씨·숙소를 함께 고려 | 조회 근거와 확인 사항이 있는 일정 |
| 계획을 받은 뒤 조건 변경 | 기존 조건을 유지하며 변경 사항 반영 | 갱신된 조건 확인 후 다시 작성한 계획 |
| 특정 정보만 필요함 | 장소·날씨·숙소 개별 조회 | 전체 계획 절차 없이 필요한 정보 제공 |

## 2. 범위

### 2.1 초기 제품 범위

- 한국어 웹 채팅과 국내 여행 계획·장소 탐색. MVP는 국내 여행으로 한정한다.
- 여행 기간은 **당일치기부터 최대 2박 3일**까지 지원한다.
- 인원은 **성인과 아동을 합산하여 최대 5명**까지 지원하며, 아동 동반 가족 여행을 포함한다.
- 이동수단은 자가용·렌터카와 기차·버스·지하철을 포함한다. 대중교통은 **구체적인 경로·환승·예상 소요 시간·요금**을 제공한다. 항공·여객선은 MVP 지원 범위에서 제외하며, 정보 조회·갱신 방식은 추가 확정한다.
- 서비스는 **모바일에 최적화된 웹앱**으로 제공한다.
- 숙소·식당은 실제 후보와 확인 가능한 정보·링크를 제공한다. 지역·종류 또는 검색 링크만 제시하는 수준으로 완료 처리하지 않는다.
- 기존 계획 수정 기능을 유지하고, 변경한 조건을 반영한 계획 수정·재작성을 MVP에 포함한다.
- 예산은 사용자 쿼리와 대화에서 언급된 내용을 파악해 계획과 비용 산정에 반영한다. 예산 언급이 없으면 예산을 추가로 요청하거나 임의의 예산 한도를 설정하지 않고, 계획에 따른 항목별 예상 비용과 총액을 제시한다.
- 여행 조건 수집 → 조건 요약 → 사용자 동의 → 외부 정보 조회 → 텍스트 계획 작성.
- 장소·날씨·숙소·운영시간·메뉴 개별 조회.
- 기존 조회 결과를 활용한 초안 카드와 끼니별 맛집 추천.
- 익명 사용자별 대화 저장·조회·삭제, 실패한 요청 재시도, 마지막 답변 다시 생성.
- 조회 진행 상황, 실행 기록, 지도·숙소 카드 등 결과 표시.

### 2.2 초기 범위에서 제외

- 숙소·교통·관광 상품의 예약·결제 대행.
- 항공·여객선을 이용하는 이동 구간의 경로·시간·요금 안내 및 항공권 가격 제공.
- 교통편 실시간 운행 정보 제공.
- 이동 경로·일정·예산의 수학적 최적화 및 정확한 도착 시각 보장.
- 계정 로그인, 기기 간 대화 동기화, 공동 편집.
- 해외 여행 계획 작성과 해외 장소·숙소·교통 정보 지원.
- 공휴일·임시 휴업을 포함한 모든 영업 변동의 실시간 반영.
- 2박 3일을 초과하는 여행과 총인원 5명을 초과하는 여행.

일정 내보내기와 공유 링크는 현재 초기 범위 제안에 포함하지 않는다. 추가 여부는 별도 결정한다.

### 2.3 현재 입력 범위

| 항목 | 현재 구현 기준 | 제품상 의미 |
|---|---|---|
| 필수 여행 조건 | 목적지, 출발일, 박수, 성인 인원, 숙소 조회 필요 여부 | 누락 상태에서는 계획 작성 동의를 진행하지 않음 |
| 선택 여행 조건 | 아동 인원, 예산, 여행 취향 | 미입력해도 필수 조건이 충족되면 진행 가능 |
| 완성형 계획 기간 | 1~13박, 즉 2~14일 | 당일치기 완성형 계획은 현재 미지원 |
| 인원 | 성인 1~20명, 아동 0~20명 | 유효성 검증 범위이며 대규모 단체여행 품질을 보장하는 수치는 아님 |
| 날씨 | 오늘 포함 16일 이내를 조회하도록 코드에서 제한 | 장기 여행 계획은 가능하나 해당 날짜의 예보가 없을 수 있음 |
| 맛집 추천 폼 | 1~14일, 출발·귀가 시각 입력 | 완성형 계획과 구분된 별도 기능 |

위 수치는 현재 코드 기준이며 합의된 MVP 지원 범위와 다르다. MVP는 당일치기~2박 3일, 성인·아동 합산 최대 5명을 지원해야 한다. 당일치기 입력과 숙소 불필요 처리, 기간 상한, 합산 인원 제한에 대한 구현 보완과 검증이 필요하다.

## 3. 사용자 흐름

### 3.1 여행 계획 작성

1. 사용자가 목적지·기간·인원·취향 등을 자연어로 입력한다.
2. 에이전트가 전달받은 조건을 누적하고 누락·오류 항목을 질문한다.
3. 필수 조건이 모이면 목적지·날짜·인원·숙소 필요 여부와 입력된 선택 조건을 요약한다.
4. 사용자가 계획 작성에 동의하거나 조건을 수정한다.
5. 동의 후 장소·날씨를 조회하고, 필요한 경우 숙소와 장소 상세 정보를 조회한다.
6. 여행 개요, 일차별 일정, 예상 비용, 준비물·주의사항을 작성한다. 추정과 미확인 정보는 구분한다.
7. 사용자는 후속 질문이나 조건 변경을 요청할 수 있다. 저장된 조건이 바뀌면 다시 요약과 동의를 거친다.

현재 상태 흐름은 `intake → confirm → compose → done`이다. 자연어의 조건 추출·동의 해석·도구 선택은 모델이 담당하고, 필수 조건 검증과 단계 전환의 유효성은 코드가 확인한다. 계획 출력의 모든 요구사항을 코드가 강제하는 것은 아니다.

### 3.2 개별 정보 조회와 기존 초안 기능

장소 추천은 지역·종류를 받아 검색한다. 날씨는 날짜를 확인하고, 숙소는 체크인·체크아웃 날짜를 확인한 뒤 조회한다. 전체 계획의 필수 조건을 개별 조회에 일괄 요구하지 않는다.

조회 결과 기반 초안 카드는 완성형 텍스트 계획과 별개다. 초안 카드와 맛집 추천에 붙는 지도 표시를 완성형 텍스트 계획에서도 동일하게 지원한다고 간주하지 않는다.

## 4. 기능 요구사항

우선순위는 초안 제안이다. **P0는 초기 제품의 필수 요건, P1은 핵심 사용성을 보완하는 요건**으로 구분한다. `구현 있음`은 코드가 존재한다는 뜻이며 아래 완료 기준의 통과 여부는 별도 평가한다. `일부 구현`은 프롬프트 지시 또는 일부 처리만으로 뒷받침되는 항목이다.

| ID | 우선순위 | 요구사항 | 완료 기준 | 현재 상태 |
|---|---|---|---|---|
| FR-01 | P0 | 여행 조건 누적 수집 | 여러 메시지로 전달한 조건을 합치고, 누락된 필수 조건만 추가 질문한다. 필수값을 임의로 채우지 않는다. | 구현 있음: 추출·질문은 모델 의존 |
| FR-02 | P0 | 입력·날짜 검증 | 범위 밖 인원·박수와 해석 불가 날짜를 거절한다. 날짜 보정이 있으면 요약에서 실제 적용 날짜를 확인할 수 있다. | 구현 있음 |
| FR-03 | P0 | 조건 요약과 작성 동의 | 필수 조건이 모이면 요약과 작성 선택지를 표시한다. 동의 전에는 완성형 계획을 작성하지 않는다. | 구현 있음: 동의 해석은 모델 의존 |
| FR-04 | P0 | 조건 변경과 계획 수정·재작성 | 기존 수정 기능을 유지한다. 목적지·기간 등 저장된 조건이 바뀌면 새 요약을 보여 주고 동의를 다시 받은 뒤 변경 조건을 반영한 계획을 작성한다. | 조건 변경·재확인 구현 있음, 수정 기능은 사용자 확인에 따라 유지; 수정 결과 품질 평가 필요 |
| FR-05 | P0 | 장소 검색 | 지역·종류에 맞는 장소명·주소·지도 링크를 제공한다. 빈 결과·오류를 구분하고 조회하지 않은 장소를 검색 결과처럼 제시하지 않는다. | 구현 있음: 답변 품질 평가 필요 |
| FR-06 | P0 | 날씨 조회 | 요청 날짜의 조회 결과와 출처를 표시한다. 예보 범위 밖·날짜 불일치·실패 상태에서 수치를 생성하거나 다른 날짜로 대체하지 않는다. | 구현 있음: 실제 답변 평가 필요 |
| FR-07 | P0 | 조건 기반 계획 작성 | 확인된 목적지·기간·인원·취향을 반영한다. 여행 개요, 일차별 활동·식사·이동, 예상 비용, 준비물·주의사항을 제공한다. 사용자 쿼리와 대화에 예산이 있으면 반영하고, 없으면 예산을 추가로 묻지 않고 항목별 예상 비용과 총액을 제시한다. 이동 시간과 비용 추정은 추정임을 밝힌다. | 일부 구현: 출력 형식은 프롬프트 지시, 예산 처리·비용 산정 품질 평가 필요 |
| FR-08 | P0 | 정보 부족·실패 처리 | 확인된 정보는 전달하고, 실패한 항목과 추가 확인 사항을 밝힌다. 빈 결과를 사실처럼 보충하지 않는다. | 일부 구현: 도구 상태 처리 및 프롬프트 지시 |
| FR-09 | P0 | 대화 저장과 사용자 구분 | 같은 익명 ID의 대화를 다시 조회·삭제할 수 있다. 다른 ID의 대화는 조회·변경·삭제할 수 없다. | 구현 있음 |
| FR-10 | P0 | 진행·오류 안내와 재시도 | 진행 상태와 최종 결과를 구분한다. 실패 시 오류 안내와 재시도를 제공하고 내부 예외·키를 노출하지 않는다. | 구현 있음 |
| FR-11 | P0 | 숙소 조회 | 필요하다고 확인한 경우 실제 숙소 후보와 확인 가능한 정보·예약 링크를 제공한다. 가격은 조회 시점 기준이며 예약·결제를 대신하지 않음을 알린다. 불필요하면 계획 작성 중 조회하지 않는다. | 구현 있음: 호출 선택은 모델 의존 |
| FR-12 | P1 | 운영시간·휴무·메뉴 조회 | 출처 URL이 있는 값만 사용한다. 미확인은 확인 필요로 표시하고, 확인된 휴무일에 해당 장소를 배치하지 않는다. 공휴일·임시 휴업 한계를 안내한다. | 일부 구현: 정보 검증은 코드, 일정 반영은 모델 의존 |
| FR-13 | P1 | 초안 카드·끼니별 맛집 추천 | 초안은 조회한 장소로 구성한다. 맛집은 입력한 기간·출발·귀가 시각으로 끼니를 정하고 후보 부재와 가정을 표시한다. | 구현 있음 |
| FR-14 | P1 | 결과 확인과 답변 다시 생성 | 해당 결과의 지도·숙소 카드·실행 기록을 볼 수 있다. 마지막 정상 답변을 저장된 질문으로 다시 생성하고 이전 답변을 대체한다. | 구현 있음 |
| FR-15 | P0 | 식당 후보 제공 | 필요한 식사에 실제 식당 후보와 확인 가능한 정보·지도 또는 상세 링크를 제공한다. 확인하지 못한 정보는 구분하고, 실제 후보 없이 지역·종류만 제시한 경우 해당 요건을 충족한 것으로 평가하지 않는다. | 장소 검색·맛집 추천 일부 구현, 전체 계획의 식사 반영 품질 평가 필요 |
| FR-16 | P0 | 대중교통을 포함한 이동 계획 | 자가용·렌터카와 기차·버스·지하철 범위에서 사용자 이동수단을 반영해 왕복·여행지 내 이동과 동선을 작성한다. 대중교통은 구체적인 경로·환승·예상 소요 시간·요금을 제공하며, 인원 및 아동 동반 조건을 비용 산정에 반영한다. 정보 출처와 추정 여부를 구분한다. 항공·여객선 이용 구간이 필요하면 지원 범위 밖임을 안내한다. | 목표 요구사항, 연동·구현 및 실제 경로 평가 필요 |

P1 항목도 현재 코드에 포함되어 있다. 우선순위는 구현 유무가 아니라 제품 검증·개선 순서를 뜻한다. 예를 들어 숙소 불필요 시 FR-11을 사용하지 않으며, 필요 시에는 숙소 정보가 FR-07의 평가 대상에 포함된다.

## 6. 성공 지표와 검증 기준

### 6.1 합의된 MVP 완료 기준

최종 MVP 개발 목표일은 2026년 11월 30일이며, 다음 두 가지를 완료 기준으로 한다.

1. **모바일에 최적화된 웹앱 형태의 서비스로 제공한다.** 모바일에서 여행 조건 입력부터 추가 질문 응답, 계획 확인과 수정까지 이용할 수 있어야 한다. 배포 환경과 지원 기기·브라우저의 세부 기준은 추가 확정한다.
2. **AI가 정보를 요약·종합하여 실질적인 여행 계획을 작성한다.** 최종 계획은 아래 8개 요소로 평가하며, 대화 과정에서는 부족한 정보에 대해 추가로 요청했는지도 확인한다. 배점, 통과점수, 평가 주체와 평가 사례는 추가 확정한다.

| 평가 요소 | 완료 판단 내용 |
|---|---|
| 기간 | 출발일·귀가일과 여행 일수가 사용자 조건에 맞고, 전체 기간의 일정이 작성되어 있는가? |
| 왕복 행선지 | 출발지에서 여행지까지의 이동과 여행지에서 귀가 목적지까지의 이동이 모두 포함되어 있는가? |
| 이동수단 | 왕복 및 여행 중 이동수단이 명시되고 사용자 조건과 동선에 적합한가? 대중교통 구간에는 구체적인 경로·환승·예상 소요 시간·요금이 포함되어 있는가? |
| 인원 | 성인·아동 합산 최대 5명 범위에서 인원과 아동 동반 조건이 일정 구성, 숙소, 식당과 비용 산정에 반영되어 있는가? |
| 숙소 | 숙소가 필요한 일정에서 숙박일과 인원에 맞는 숙소 계획이 빠짐없이 포함되어 있는가? 불필요한 경우에는 그 조건을 반영했는가? |
| 식당 | 여행 기간과 출발·귀가 시각에 필요한 식사가 빠지지 않도록 식당 계획이 작성되어 있는가? |
| 실질적 예상 비용 | 예산 입력 여부와 관계없이 교통·숙박·식비·입장료 등 필요한 비용과 총액을 제시하는가? 금액이 현실적으로 산정되어 있고, 인당·전체 기준 및 추정 근거가 명확한가? 사용자가 예산을 제시했다면 반영했는가? |
| 동선 작성 | 왕복 이동과 일자별 방문지·숙소·식당의 연결 순서가 작성되어 있으며, 이동·체류 시간을 고려해 실행 가능한가? |

위 표는 합의된 평가 요소를 판정 가능한 문장으로 정리한 초안이다. 구체적인 채점 방법과 누락·오류의 감점 기준은 평가 명세서에서 정한다. 이는 목표 요구사항이며 현재 구현이 모든 요소를 충족한다는 의미는 아니다. 왕복 행선지·이동수단의 구조화된 수집과 비용 산정·동선 검증은 추가 구현 필요성을 확인해야 한다.

점수는 MVP 품질을 평가하기 위한 기준이다. 사용자 화면에 여행 계획의 점수를 표시하는 기능까지 합의한 것은 아니다.

### 6.3 측정 지표

**추가 질문 적절성은 평가에 포함한다.** 필수 정보 누락·모호한 입력·서로 충돌하는 조건이 있을 때 필요한 내용을 추가로 요청하는지 확인한다. 최종 계획만 평가하지 않고, 입력부터 계획 작성까지의 대화 이력을 함께 확인한다. 세부 채점 기준은 아래 제안으로 두고 평가 명세서에서 확정한다.

- 누락된 필수 정보를 구체적으로 질문하며 임의로 채우지 않는다.
- 이미 받은 정보나 사용자가 답한 항목을 불필요하게 반복 질문하지 않는다.
- 날짜·인원 등 모호하거나 충돌하는 조건은 확인한 뒤 진행한다.
- 필수 정보와 선택 정보를 구분하고, 선택 정보 미입력만으로 계획 작성을 막지 않는다.
- 예산은 사용자 쿼리와 대화에서 파악하며, 언급이 없다는 이유로 추가 질문하지 않고 예상 비용을 제시한다.
- 개별 장소·날씨·숙소 조회에는 해당 요청에 필요한 정보만 질문한다.

아래 지표는 측정 계획이다. 현재 수치·사용자 효과·목표 달성을 주장하지 않는다. 평가 명세서에서 시나리오와 표본 수를 고정한 뒤 측정한다.

| 지표 | 측정 방식 | 목표 상태 |
|---|---|---|
| 필수 조건 수집 성공률 | 조건 누락·분할 입력·오류 입력 시나리오 중 적절하게 수집·검증한 비율 | 목표치 미정 |
| 추가 질문 적절성 | 정보 누락·모호함·충돌 사례에서 필요한 확인 질문을 했는지, 임의 가정·불필요한 반복 질문 없이 진행했는지 대화 이력으로 채점 | 평가 포함 확정, 배점·통과 기준 미정 |
| 동의 절차 준수율 | 동의 전 작성 금지와 조건 변경 후 재확인을 모두 지킨 비율 | 필수 평가 사례 전부 충족 제안 |
| 계획 완성률 | 작성에 동의한 평가 사례 중 FR-07의 구성을 제공한 비율 | 목표치 미정 |
| 조건 반영률 | 목적지·기간·인원·입력한 취향을 충족한 사례 비율 | 목표치 미정 |
| 근거 없는 정보 제시 건수 | 예보 없는 날씨 수치, 조회하지 않은 숙소 가격 등 사례별 위반 수 | 필수 평가 사례에서 0건 제안 |
| 실패 처리 적합률 | 예보 부재·검색 결과 없음·인증 오류·시간 초과를 적절하게 안내한 비율 | 목표치 미정 |
| 데이터 격리·삭제 | 다른 익명 ID 접근 거절 및 삭제 후 재조회 불가 여부 | 필수 평가 사례 전부 충족 제안 |
| 응답 시간·비용 | 요청별 첫 상태 표시·완료까지 소요 시간, 모델·도구 사용량과 비용 | 기준선 측정 후 목표 확정 |
| 사용자 유용성 | 실제 사용자에게 수정 필요 정도와 계획 활용 의향 확인 | 조사 방식·목표치 미정 |

### 6.4 초기 검증 완료 조건 제안

1. 합의한 P0 요구사항별 정상·누락·오류·조건 변경 사례를 평가한다.
2. 동의 절차 우회, 다른 사용자 데이터 접근, 비밀키 노출, 확인되지 않은 값을 조회 사실로 단정하는 중대 문제는 필수 평가 사례에서 발생하지 않아야 한다.
3. 실제 모델과 외부 서비스를 연결한 계획 작성 및 실패 사례를 확인한다.
4. 브라우저에서 조건 요약·동의·결과·대화 관리·재시도를 확인한다.
5. 결과에 코드 버전, 모델·설정, 실행일, 평가 데이터와 미해결 항목을 남긴다.

이는 검토할 출시 판단 기준이며, 현재 출시 승인이나 검증 완료를 의미하지 않는다.

## 7. 개발·문서 정리 단계

**최종 MVP 개발 목표일은 2026년 11월 30일이다.** 현재 계획 기준의 목표일이며, 세부 단계별 일정과 담당자는 미정이다. 현재 구현을 기준으로 요구사항의 합의와 검증을 진행하고, 목표일까지 완료할 MVP 범위는 본 문서의 우선순위와 평가 기준을 검토해 확정한다.

| 단계 | 산출물 | 종료 기준 |
|---|---|---|
| 1. 제품 범위 합의 | 본 PRD | 대상 사용자, 범위, 우선순위, 필수 검증 사례 확정 |
| 2. 책임과 데이터 정의 | AI 역할 명세서, 데이터 명세서 | 모델·코드 책임, 필드·출처·검증·저장 정책과 미정 사항 정리 |
| 3. 시스템 계약 정리 | 시스템 설계서, API 명세서 보완 | 현재 구현과 문서 간 차이 확인 및 수정 |
| 4. 평가 준비·실행 | 평가 명세서, 평가 결과 | 자동 테스트와 실제 연동·화면 평가를 각각 기록 |
| 5. 개선 범위 확정 | 우선순위별 개발 항목, README 갱신 | 미충족 기준을 작업으로 정리하고 지원 범위를 문서에 반영 |

## 8. 주요 제약과 결정할 사항

| 구분 | 확인된 제약 또는 질문 | 후속 조치 |
|---|---|---|
| 일정 품질 | 다일 일정의 조회 범위와 방문지 분배, 이동 시간·예산의 현실성을 자동 검증하지 않음 | 기간별 평가 및 코드 검증 추가 필요성 판단 |
| 날짜별 날씨 | 계획 작성 안내는 출발일 날씨 조회를 지시함. 여행 전체 날짜의 날씨 반영은 보장되지 않음 | 일자별 예보 조회를 필수로 할지 결정 |
| 모델 의존 | 의도·조건·동의 해석과 도구 선택, 출력 형식·정보 반영은 모델 성능에 영향을 받음 | 실제 모델 평가 후 보완 범위 결정 |
| 동의 의미 | 명시적으로 동의하지 않은 애매한 표현의 처리 기준이 충분히 정의되지 않음 | 동의·거절·질문·조건 변경 사례 정의 |
| 당일치기·기간·인원 | MVP는 당일치기~2박 3일과 성인·아동 합산 최대 5명을 지원해야 하나 현재 검증 범위와 다름 | 0박 입력·숙소 생략 흐름, 최대 2박·합산 5명 제한 구현 및 경계값 평가 |
| 부분 수정 | 특정 일차만 수정하고 나머지 일정을 보존하는 동작은 프롬프트 수준의 지시가 있음 | 요구 수준과 검증 방식 결정 |
| 예산·예상 비용 | 사용자 쿼리·대화에서 예산을 파악하고, 언급이 없으면 추가 요청 없이 예상 비용을 제시한다. 현재 예산은 문자열로 보관하며 총비용 계산·초과 검증이 없음 | 항목별·총액·1인당 기준과 추정 근거를 정리하고, 예산 언급 유무별 처리와 산정·검증 방식 구체화 |
| 정보 최신성 | 외부 검색·숙소 조회·캐시에 따라 실제 방문·예약 시점과 차이 가능 | 조회 시점·출처·재확인 안내 평가 |
| 외부 의존성 | 모델·카카오·날씨·숙소·웹 검색의 장애·사용량·비용이 영향을 줌 | 실패 시나리오와 사용량 기준 마련 |
| 데이터 정책 | 대화·캐시·관측 로그의 보존 기간, 백업 포함 삭제 범위 미확정 | 데이터 명세서에서 확정 |
| 성능·비용 | 목표 동시 사용자 수, 지연 시간, 사용자당 비용 상한 미정 | 실측 후 운영 기준 합의 |
